# Manus 手套遥操 XHand — 技术概要

一页纸的对外说明:平台、通信、标定方法、结果。
实现细节和踩坑清单见同目录 [`MANUS.md`](MANUS.md)。

---

## 1. 目标

用人手遥操作真实 XHand,判定 repose-cube 任务的 sim2real gap 属于哪一类:

- 人遥操能转动 cube → **硬件可行**,问题在感知-动作闭环(策略/观测)
- 人遥操也转不动 → **硬件/接触本身做不到**,该改指面材质、物体表面或任务定义

策略在仿真中成功率 96%,真机卡死在"平面-平面接触"。已通过仿真消融排除 cube 尺寸、质量、穿透、起始位姿、逐连杆摩擦等因素。

## 3. 授权约束(决定了整个架构)

Manus 的 license 按功能组件授权,绑定硬件 dongle。本套设备实测:

| 组件 | 状态 |
|---|---|
| recording / exporting / advanced exporting | ✅ |
| **Unity plugin** / Unreal plugin / MotionBuilder plugin | ✅ |
| **sdk**(C++ SDK 远程模式) | ❌ |
| **integrated**(C++ SDK 直连 dongle) | ❌ |

**后果:官方 C++ SDK 完全不可用。** `libManusSDK.so` 与 `libManusSDK_Integrated.so` 均被 license 拦截(integrated 模式实测能取到 110 Hz 数据后被拒),随 SDK 提供的 ROS2 包使用同一动态库,同样不可用。

由于 Manus Core 仅支持 Windows,且 Unreal 插件体积 40 GB+、MotionBuilder 为付费软件,**Unity 插件是唯一免费可行的数据出口**。

## 4. 通信架构

```
        Windows                                    Linux (Ubuntu 22.04)
 ┌─────────────────┐
 │   Manus Core    │◀── 无线 dongle ── 手套
 └────────┬────────┘
          │ 进程内 (C# 插件)
 ┌────────▼──────────────┐
 │  Unity 6000.0.83f1    │
 │  (Play 模式)           │
 │                       │        JSON over UDP
 │  ManusUdpBridge.cs ───┼── :9881 ──▶ manus_node.py ──────┐
 │   20 通道关节角        │  (广播)                          │
 │                       │                                  │ 二进制 UDP
 │  ManusSkeletonBridge  │                                  │ :51234
 │       .cs ────────────┼── :9882 ──▶ manus_skel_node.py ──┤ (61 字节/帧)
 │   3D 骨架位姿树        │  (广播)                          │
 └───────────────────────┘                                  ▼
                                                    real_node.py
                                              RS-485 @3M, /dev/ttyUSB0
                                                          │
                                                          ▼
                                                    真实 XHand
```

### 4.1 Unity → Linux(应用层 JSON over UDP)

发往**子网广播地址** `192.168.1.255`,接收端 bind `0.0.0.0`。
采用广播而非单播:Linux 的 DHCP 租约变更曾导致整条链路静默中断,而每一层自查都显示正常。广播后操作者机器的 IP 不再位于关键路径。

**通路 A — ergonomics(端口 9881)**,约 90 Hz:
```json
{"ergo": [20 个浮点数, 单位度]}
```
5 指 × (MCP 张开 / MCP 弯曲 / PIP 弯曲 / DIP 弯曲),右手位于 `float[40]` 的 offset 20。

**通路 B — 3D 骨架(端口 9882)**,约 60 Hz:
```json
{"skel": [[x,y,z, qx,qy,qz,qw], ...],
 "meta": [[chainType, fingerJointType, nodeId, parentId], ...],
 "ids":  [nodeId, ...]}
```
25 个节点。注意 **`skel` 是父节点相对位姿(局部坐标)**,不是世界坐标 —— 接收端需做正运动学。元信息随每帧发送,使节点语义由接收端解析,修改对应关系无需改动 Unity。

### 4.2 Linux 内部(二进制 UDP,`protocol.py`)

```c
struct {                    // 小端,无填充,共 61 字节
    uint32  seq;            // 帧计数
    float64 t;              // 发送时刻
    uint8   valid;          // 1 = 本帧跟踪有效
    float32 q[12];          // 12 个关节目标角(弧度)
};
```

纯标准库实现,两个 conda 环境均可导入。选用 UDP 而非 TCP:遥操作只需最新样本,丢包由下一帧补上,不能有队头阻塞。

**设计要点:两个 manus 节点与相机路径的 `perception_node.py` 输出同一协议**,因此互为平行替代品。下游 `real_node.py`(真机)和 `teleop_sim.py`(Isaac Sim)无需任何修改。

### 4.3 Linux → XHand(RS-485)

| 项 | 值 |
|---|---|
| 物理层 | RS-485 over USB(FTDI FT232R),3 Mbaud |
| 帧头 | `0xAA55` |
| 命令 | `0x02` = 位置控制(同一命令的响应回传实测关节角) |
| 负载 | 12 × `FingerCommand`,每个 24 字节 |
| 校验 | CRC16-XMODEM |
| 回包 | 12×24 + 5×384 = 2208 字节(12 关节状态 + 5 指尖传感器) |

> 固件对 `0x13`(版本查询)不响应,`0x02` 正常。判断手是否上电应使用 `real_node.py --read`(零增益零力矩的只读查询,不产生运动)。

## 6. 标定方法

### 6.1 问题

手套提供 20 维手部特征,XHand 有 12 个关节。需建立 20 → 12 的映射,涉及三组未知量:**通道归属**(哪个特征驱动哪个关节)、**符号**(方向)、**量程**(人手行程 → 关节行程)。

### 6.2 先后尝试与失败原因

| 方法 | 结果 |
|---|---|
| 按 SDK 通道名称接线 + 解剖学名义量程 | 失败:名义量程比实测宽达 5 倍,握拳只能达到约 1/3 行程;拇指方向错误 |
| 按 URDF 关节轴几何推导方向 | 失败:掌坐标系轴向判断错误(四指根部沿 x 排列、z 为手指伸出方向、掌法线为 y),据此推出的结论全部无效 |
| 实测各通道真实行程 | 量程问题解决,方向仍错 |
| 依据实测数据调换拇指通道 | 仍错 |
| 3D 骨架 + DexPilot 几何重定向 | 架构正确但未完成:手掌规范坐标系的基向量约定与 MANO 不一致 |

**共同问题:全部在推断手套侧的语义。** 三组未知量互相纠缠,且"归属错"与"符号错"在真机上表现完全相同,只能逐项试错;每轮验证需数分钟且必须有人在机器人旁。这是搜索过程,不收敛。

### 6.3 采用的方法:机械手示教 + 岭回归

**将标定方向反转 —— 由机械手提供标签。**

```
1. 程序驱动 XHand 到指定关节向量 q        ← 标签由指令给出,精确已知
2. 操作者观察机械手,用戴手套的手模仿      ← 对应关系由人眼建立
3. 记录该姿势下的 20 维手部特征 e
4. 重复 19 个姿势,岭回归拟合 e → q
```

**19 个姿势**覆盖:全张开、握拳、四指分别单独弯曲、半弯、1/4 弯、食指侧摆两端、拇指三个自由度各自两端、拇指对掌、捏合、指点、勾状。设计原则是每个自由度都有单独激发的姿势,再辅以若干组合姿势提供真实耦合。

**实现细节:**
- 特征先做标准化再回归。岭回归对所有系数等权惩罚,而各通道量纲相差 10–130 度,不标准化会使正则强度沦为量纲的偶然产物(实测表现为最优 α 顶到搜索上界)。
- 正则系数 α 由**留一交叉验证**在 10⁻³–10⁴ 上选取。
- 拟合后将标准化折回,输出的仿射映射 `q = A·e + b` 直接消费原始特征。
- 原始样本 `E`、`Q` 一并存档,支持 `--refit` 离线重新拟合,无需重复示教。
- 两路数据源均可用:ergonomics 通道直接使用;3D 骨架则在本地计算等价的 20 维特征(每指两个骨节夹角 + 出掌面仰角 + 掌面内方位角)。

**耗时:约 2.5 分钟 / 人。**

### 6.4 该方法的两个关键性质

**① 无需任何关于手套侧语义的假设。** 通道归属、符号、量程、交叉耦合全部由回归解出。

**② 拟合不佳退化为"关节响应弱",而非"方向相反"。** 回归不会产生与数据相悖的符号翻转,低 R² 仅表示响应微弱。这与手写映射的失效模式有本质区别 —— 后者一旦出错即为整体反向,可能将物体弹飞。这使得标定质量不足时系统仍然安全。

## 7. 结果

### 7.1 标定精度(首次实测,19 姿势)

| 关节 | R² | 主导特征 |
|---|---|---|
| `index_joint1` | 0.928 | index.mcp, index.pip |
| `index_joint2` | 0.972 | index.pip, index.mcp |
| `middle_joint0` | 0.954 | middle.pip, middle.mcp |
| `middle_joint1` | **0.985** | middle.pip |
| `ring_joint0` | 0.950 | ring.pip |
| `ring_joint1` | 0.981 | ring.pip |
| `pinky_joint0` | 0.907 | pinky.pip, pinky.mcp |
| `pinky_joint1` | 0.966 | pinky.pip |
| `thumb_joint2` | 0.861 | thumb.pip, thumb.dip |
| `thumb_joint0` | 0.758 | thumb.spread, thumb.pip |
| `thumb_joint1` | 0.489 | — |
| `index_joint0` | 0.298 | — |

**四指 8 个关节 R² 均在 0.907–0.985。**

**结构自洽性验证:每个四指关节均由其自身手指的特征主导** —— 该结构完全由回归从数据中得出,未向算法提供任何先验对应关系。此为映射正确性的独立佐证。

两个低分项:
- `index_joint0`(食指侧摆)总行程仅 ±10°(±0.175 rad),机械手上视觉差异极小,操作者无法可靠复现。对本任务影响有限。
- `thumb_joint1` 在示教时易与其他拇指自由度耦合。

> 上表为特征标准化修复**之前**的结果(当次 α 顶到上界 1000)。修复后合成数据上 α 降至 0.1,尚未重新实测。

### 7.2 链路性能

| 环节 | 实测 |
|---|---|
| Unity → Linux(ergonomics) | 64–90 包/秒 |
| Unity → Linux(3D 骨架) | ~60 包/秒 |
| manus_node 重定向 + 发布 | 60 Hz(上限设定值) |
| RS-485 下发 | 50 Hz |
| 骨架 FK 校验 | wrist→中指尖 0.211 m,食指根→小指根 0.060 m(符合真实手部尺寸) |

### 7.3 安全层(始终启用)

URDF 关节限位夹紧 · 每关节速度限幅(默认 2.5 rad/s,首跑建议 1.0)· 目标值 EMA 平滑 · 首个目标取自实测手位(避免使能瞬间跳变)· 断流看门狗(> 2 s 保持当前位姿,不松开、不抽搐)· 固件侧力矩上限(默认 300,首跑建议 150)。

## 8. 结论性经验

**标定方向的选择决定了错误的代价。**

推断手套侧语义:出错只能在真机上试错,单轮数分钟,且无法区分是归属错还是符号错。
由机械手示教:标签精确已知,对应关系由人眼建立(这是人最可靠、算法最不可靠的判断),其余交由回归;且拟合不佳只表现为响应迟钝,不会方向相反。

该方法不依赖手套型号,可直接迁移至其他数据手套或其他多指手。
